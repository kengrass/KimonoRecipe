# 公開検索のスケール方針

現行サイトでは検索が重くなりがちだった。新契約（絞って1ページ返す）でも、**件数が増える前提で先に抑える**。  
Redis 専有や検索エンジン常時並走は、効果が数字で見えるまで入れない（ランニング優先）。

関連: [`LIST_QUERY_ARCHITECTURE.md`](./LIST_QUERY_ARCHITECTURE.md) ・ コスト方針: `.cursor/rules/running-cost-aware-design.mdc`

---

## 1. 守る前提（契約）

| 項目 | 内容 |
|------|------|
| 返す量 | `data` は **1ページのみ**（既定 `per_page=12`、上限をサーバでも clamp） |
| 絞り込み | **DB／API 側のみ**。全件取得→フロント絞りは禁止 |
| `cat`（コーデ） | コーデ行にカテゴリは無い → **紐づく公開アイテムの `category`** でヒット |
| `cat`（アイテム） | `items.category` 直指定 |
| キャッシュ | **公開確定のみ**。非公開・会員フィードは載せない。公開→非公開は即無効化できる経路だけ |

---

## 2. まずやる（安く効く）

本番 MySQL／RDS でも同趣旨。spike は試作で先行実装済み。

### 索引（必須級）

| 用途 | 例（MySQL イメージ） |
|------|----------------------|
| 公開アイテム新着 | `(visibility, created_at)` |
| 公開アイテム＋カテゴリ | `(visibility, category, created_at)` |
| 公開本コーデ新着 | `(visibility, is_temp, created_at)` |
| 性別／帯結び | `(visibility, is_temp, gender, created_at)` / `(…, obi_knot, created_at)` |
| 紐付け逆引き | `coordinate_items(item_id)`（コーデ側 PK `(coordinate_id, item_id)` とセット） |

コーデ `cat` はだいたい:

```text
items (visibility, category) → coordinate_items(item_id) → coordinates 公開条件
```

**カテゴリを先に絞ってから紐付ける**（選択性が高い）。全公開コーデをなめて EXISTS する形は、索引なしだと現行同様に重くなりやすい。

### クエリ形

- フィルタ列は **等価・IN・範囲** を優先
- `tags_json LIKE '%…%'` や先頭 `%` の `q` は **フルスキャン寄り**とみなす（補助条件）
- `EXPLAIN` で「公開＋カテゴリ索引 → 紐付け」になっているか確認

### `COUNT(*)` と深い `OFFSET`

| 問題 | 対策の段階 |
|------|------------|
| 毎回の厳密 `total` | 当面は契約どおり返す。重くなったら **人気条件の total 短 TTL キャッシュ**（公開のみ） |
| 大きな `page` | UI はページネーション維持。必要なら **最大ページ上限**や「これ以上は条件を足す」を製品判断 |
| cursor 化 | API 契約変更が要るので **後続**（今は OFFSET のまま） |

---

## 3. まだ入れない／慎重

- **全文検索エンジン常時並走**（OpenSearch 等）… `q` が本命の苦情になってから。RDS の FULLTEXT や生成カラムの方が先に安いことが多い
- **Redis 専有**… 一覧 total／人気クエリの効果が測れてから
- コーデへのカテゴリ非正規化テーブル… EXISTS／IN が実測で足りないときだけ（更新・非公開整合が負債）
- 検索結果の長期 CDN… 条件付き URL はキャッシュキーが増える。載せるなら短 TTL＋公開範囲変更時の無効化設計が先

---

## 4. 計測（入れるタイミング）

1. 公開コーデ／アイテムがおおむね **1万→数万** になったら、代表クエリ（`cat` のみ / `g`+`season` / `q`）のレイテンシを取る  
2. `EXPLAIN ANALYZE`（または同等）で索引未使用がないか見る  
3. 遅いのが `COUNT` か `OFFSET` か `LIKE q` かを切り分ける  

切り分け前にインフラを足さない。

---

## 5. 実装チェック（正式棚）

公開一覧の手続き（[`../spike/docs/API.md`](../spike/docs/API.md)）に加え:

- [ ] 上記索引が本番相当にある  
- [ ] コーデ `cat` は公開アイテム経由（非公開アイテムではヒットさせない）  
- [ ] `per_page` サーバ上限（例: 50）  
- [ ] 検索スパゲッティの全件ロードを移植していない  
- [ ] 重い `q` を他条件なしで連打しても API／DB が落ちない（必要ならレート制限は WAF／入口側）
