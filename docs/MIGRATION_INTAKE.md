# 移行の受け渡し仕様（新DBに載せる形）

**出元のテーブル名はこちらでは指定しません。**  
既存側のどこから取るかはエンジニア側の判断です。  
こちらが定義するのは、**新DB／新APIが受け取るレコードの形**です（[`NEW_DB.md`](./NEW_DB.md) に依拠）。

方針の1枚: [`FOR_ENGINEERS.md`](./FOR_ENGINEERS.md)

---

## 0. 読み方

| 用語 | 意味 |
|------|------|
| **渡してほしい** | 初回移行で新DBに載せたいもの |
| **任意／後続** | 無くても起動はできる。あると体験が続く |
| **渡さない** | 新系に持ち込まない |
| **要協議** | 形は決めたいが、運用判断が要る |

ID（`users.id`・投稿 id 等）は、可能なら **現行公開URLの ID を維持**したいです（`/c/{id}` `/i/{id}` `/m/{id}` の連続性）。難しければ対応表を協議します。

パスワードは **既存ハッシュを安全に移せるか**、または **初回ログインで再設定か**を協議（アルゴリズムが違うと素通しできない）。

### 1.5 画像資産 `images`（推奨）

投稿の `images` だけでも起動はできますが、未使用プールや再クロップのため **資産行**があるとよいです。

| フィールド | 必須 | メモ |
|------------|------|------|
| `id` | ○ | |
| `owner_id` | ○ | |
| `master` / `square` | ○ | ファイルまたは URL。原寸の永久保存はしない。処理方針は下の「クロップ」注意 |
| `in_unused_pool` | | 投稿未参照なら true にしてよい |

**クロップ／過去画像の既定案:**

| 種類 | 入力 | 処理 |
|------|------|------|
| **投稿に載っている画像** | 旧の**正方形** | メタ削除→長辺リサイズ→`master`。`square` はマスターから（実質同一可） |
| **未使用プール** | 可能なら旧の**オリジナル／広い画像** | 同じくメタ削除→長辺リサイズ→`master`＋正方形派生。正方形しか無いときだけ正方形由来で妥協 |

投稿済みは大きく切り直す需要が低い。未使用はこれからクロップするため、広い入力が望ましい。原寸の永久保存はしない。

**容量面の副次効果（見込み）:**  
投稿分は正方形由来、未使用だけ広い入力に限定すれば、全体をオリジナル二系統で持つより容量を抑えやすい。確認後に旧オリジナルを捨てられればなお良い。

## 3.5 移行時に同意してもらうポイント（ユーザー向け文言案）

移行ボタン／案内メールで示す用。実装前の原稿。

**移行すると、つぎの内容に同意したものとします。**

1. **あたらしいサイトへ移ります**  
   移行が始まってから完了するまで、いまのサイトも新しいサイトも使えません（画像の取り込み完了までお待ちください）。完了後は**新しいサイトだけで**ご利用ください。いまのサイトにはログインできなくなります。  
   また移行のあいだ、いまのサイト上でもご投稿が一覧などから見えなくなることがあります（完了後は新しいサイト側で表示されます）。取り込み途中の欠けた状態は、他の方の画面にも出しません。

2. **画像について**  
   これまでの**投稿済み**画像は、表示用の正方形イメージをもとに新しいサイト用へ取り込みます。大きな元画像は原則持ち込みません。そのため、あとから大きく切り直すことはできない場合があります（いま見えている写真そのものは引き継ぎます）。  
   **まだ投稿に使っていない画像（未使用）**は、あとから切って使うことがあるため、可能なかぎり元の大きい画像をもとに取り込みます。

3. **Myフォルダ・Myカテゴリはなくなります**  
   新しいサイトには Myフォルダ／Myカテゴリはありません。整理の枠組みは引き継がれません。

4. **ブランド機能はなくなります**  
   ブランドに関するこれまでの分け方・表示は、新しいサイトでは使えません。

5. **色の系統での探し方・保存はなくなります**  
   「色調」を前提にした検索や保存のしかたは、新しいサイトの対象外です。

6. **いいね・フォローについて**  
   引き継ぎます。まだ新しいサイトに移っていない相手や投稿については、しばらく表示されないことがあります。相手が移行すると、あらためてつながって見えるようになる場合があります。

7. **ログインについて**  
   新しいサイトで、あらためてログイン（またはパスワードの設定）が必要になる場合があります。案内に従ってください。

8. **一度きりです**  
   移行完了後、いまのサイト側のデータは退会と同様に整理されることがあります（メールの無効化や画像の削除など）。いまのサイトへ戻すことは想定していません。

---

補足（案内文に必須ではないが、問い合わせ用）:

- 仮コーデ・非公開の扱いは新しいサイトのルールに従います（仮は公開一覧に出しません）。  
- 画面の見た目や操作は新しくなっています。

## 4. 並走タイムライン（案）

**なぜ今やるか（企画判断）:** 重いが先延ばしするほど画像・会員が増え、移行がさらに難しくなる。今の規模感（対象数百・大口は数十人オーダー）のうちに進める。あわせて、正方形中心の取り込みと旧オリジナルの整理ができれば、**長期の保存容量を抑えられる**見込みもある。

**旧側の改修・開発は最小限**にし、足りないところは **新側の取込・管理画面／メモ・運用手順**でカバーする（詳細は §5「旧側は最小限」）。

新サイト・オープンを起点にしたイメージ。期間は目安（協議で前後可）。

| 時期 | 旧サイト | 新サイト | 移行 |
|------|----------|----------|------|
| **（任意）クローズド先行** | 従来どおり | Basic／招待のみ等で **限定公開** | **管理代理のみ**（自己移行オフ）。検証・口コミ用 |
| **大口先行（目安: 画像1000超 ≈50人）** | 従来どおり（移行中・済はログイン不可） | 稼働（限定 or 一般は協議） | **管理代理で個別対応し切る**。自己移行オフ。**この完了を一般3ヶ月の起算に** |
| **一般移行期（約3ヶ月）** | **新規登録停止**。未移行は利用可 | 一般公開。移行済みはこちら | **代理がメイン**。自己移行は **この期間だけ**サブで可（無くても可）。起算は大口完了後 |
| **（推奨）同期間** | — | **新規登録動線も閉じる** | 誤って新だけ登録→旧データと二重になり応対が重いのを避ける |
| **一般期終了後〜** | **Web から切り離し（クローズ）** | 本運用。ここで **新規登録を開けてよい** | **問い合わせ→管理代理のみ**（自己移行オフ） |

狙い:

- オープン後の新規は「旧に増えない」（登録停止）
- 移行期間中は「新だけの迷子アカウント」を増やさない（新の新規も一旦閉じる）
- 期限後は旧を表から消し、残りは問い合わせで個別対応

カバレッジの見立て（企画側の感覚・要実測）:

- **移行の主対象は数百ユーザー規模**（全会員を機械一括する前提ではない）
- **一般向け3ヶ月**は、大口（画像1000超 ≈50人）を対応し終えてから数え始めるのが現実的  
- その3ヶ月で、少なくともアクティブの半数はカバーできる見込み  
- **SNS 等の告知**に加え、必要なら **一人ずつメール**でもよい（運用手間はかける前提）  
- 残りは一般期終了後の問い合わせ移行で拾う  

残リスクの本丸は人数より **大口の画像枚数をジョブが無事処理しきれるか**（50人帯・とくに3000超／最大級で潰す）。

規模感（企画側の把握・概数）:

| 画像枚数 | ユーザー数（およそ） | 扱い |
|----------|----------------------|------|
| 1000超 | **約50** | **一般3ヶ月の前に**個別案内・管理代理で対応し切る帯。枚数は全体（約33万）の **だいたい1/3** という感覚 |
| 3000超 | **約13** | 最優先。試験＋画像事前取込（案 B）の先頭組 |
| 最大 | **約12235枚**（1人） | 分割ジョブの最悪ケース。試験移行の本命 |

つまり一般解禁前に、人数は少ないが **容量・処理時間の大きな塊**を先に消化できる見込み。残りの2/3は人数の多い一般帯に分散する。

#### 移行方式（確定）

**ユーザー単位＋大口先行（案 B）** で進める。  
（外部レビューの一括切替案は不採用。理由: 合意なき一括はデグレ期間と相性が悪い／旧改修最小・代理運用と整合。）

#### 大口の事前取込（方針: 案 B）

**画像を先に大方移し、通常移行の再実行（既存スキップ）で穴を埋める。** メタの差分エンジンや事前専用UIは作らない。

**なぜ画像だけ先か（制約）**

- 同意前に旧を止めないとメタは動き続ける → メタ先載せはすぐ古い  
- 画像は ID 単位で足せる。紐付け差分は面倒なので事前には触らない  
- 移らない／解約なら新のそのユーザー一式を削除すればよい（容量のゴミ）

**事前（手動・エンジニア依頼）**

- 対象ユーザー **ID を指定**して依頼（頻繁には頼めない前提）  
- 多少エラー前提で **大方**の画像バイナリを新へ（非公開の会員殻にぶら下げる）  
- 進捗UIは不要。**Backlog チケットに uid ごと** `全量件数 / 成功 / エラー` を残す（ジョブ終了時のログ／集計で足りる）  
- エラー ID 一覧があれば再実行しやすい（任意）

**通常移行（同意後・ロック後）**

- メタ＋紐付けを載せ、画像は **既にある ID はスキップ**、欠け／以前エラー分だけ取得  
- **新管理**の移行ボタンで起動。同画面に `全量 / 成功 / エラー` を出し、**100%（不足ゼロ）になるまで再実行**して穴埋めする  
- いわゆる「差分取込」は専用エンジンではなく、**冪等な再実行**と同じもの  
- 旧側は **読み出し（抽出）と解約／表示名・メモ**など最小限だけ。移行ボタンや進捗UIは旧に足さない

移行と並行して **解約（退会）も受け付ける**案あり（移さず終わる選択）。導線・データ消去範囲・旧／新のどちらで受けるかは **要検討**。

**クローズド先行**もあり（ロイヤリティ層だけ先に案内 → 一般オープン）。利点は本番前の実利用フィードバック。コア層が先に移って **旧が急速に過疎る／体験が落ちる**ことはあり得るが、**問題にしない**（移行を優先する）。

注意:

- 3ヶ月で移らなかった会員は、旧クローズ後は **問い合わせ移行**が唯一の道になる → 事前告知・リマインドが必要
- 「Web から切り離す」≠ 即データ削除。問い合わせ移行のため **旧DB／バックアップは一定期間保持**したい
- 新の新規登録を閉じる期間はビジネス判断（新規獲得を止めるトレードオフ）。閉じない場合は「新で登録した人と旧会員の名寄せ」運用が別途必要

## 5. 実施単位・起動方法（方針）

**ユーザー単位で移行する**想定です（全会員一括のビッグバンは必須にしない）。

1人分のセット例: その会員の `users` 行 ＋ 所有する items／coordinates／images／紐付け ＋（任意）その人起点のいいね／フォロー。

**いいね／フォローと「先が未移行」（推奨・確定寄り）:**  
相手・対象が新DBにいなくても **行はそのまま載せる**。「相手が移ってきたら足す」専用ジョブは不要。

- 一覧・カウントは **存在する相手／投稿だけ JOIN** → 先が無ければ何も出ない  
- あとから同じ ID で相手が移行すれば、**追加処理なしで自然につながる**  
- 先が来ない行は参照切れとして残るが、これは **相手が退会しているときと同じ種類のゴミ**（既に許容しているモデル）。新しいデメリットはほぼない  
- 厳密な外部キーで挿入できない場合は、いいね／フォロー側は必須 FK にしない  

捨てる案より実装が単純なので、載せて JOIN で無視、でよい。

並走中は「新系に移った会員」と「まだ既存のみ」が混在しうる。

### 起動（UI）

| 優先 | 経路 | だれが | どこ |
|------|------|--------|------|
| **メイン** | **代理移行** | 運営 | 問い合わせ／個別案内ベースで **管理画面の移行ボタン** |
| **サブ** | **自己移行** | 既存会員本人 | マイページの移行ボタン（**期間限定**） |

どちらも中身は同じ「1ユーザー分の取込」。二重実行は冪等または拒否（既移行なら何もしない／案内）。

**代理を主・自己は従（方針）:**

- 開発工数・同時押し集中リスクを抑える  
- **最悪、代理移行だけでも成立**させてよい（自己移行は後付け／省略可）  
- 自己移行を付ける場合も **一般移行期だけの期間限定機能**  
  - クローズド先行・大口先行のあいだは自己移行オフ（管理代理のみ）  
  - 一般期終了後（旧クローズ〜問い合わせフェーズ）も自己移行オフ（再び管理代理のみ）

### 移行後の利用先（理想）

**実行が成功したら、その会員は現行サイトでは使えなくする。**  
以降は **新サイトにログインして利用開始**してもらう（現行への戻りは想定しない）。

| 段階 | 理想の挙動 |
|------|------------|
| 未移行 | 現行サイトのまま利用可（新系は未ログイン／未移行扱い） |
| **移行中**（希望〜完了前） | **本人は旧・新ともログイン不可**（案内＋画像カウントダウン可） |
| 移行成功直後〜移行後 | **新サイトのみ**ログイン可。旧はログイン不可／新へ誘導 |

**他の閲覧ユーザーへの影響（重要）:**  
メタだけ先に新DBへ載せると、本人は使えなくても、新サイトの**他人の一覧・詳細に「投稿はあるが画像が無い」**が出うる。  
そのため移行中のその人のコンテンツは、画像不足一覧が空になるまで **公開フィード／公開詳細に出さない**（非公開扱い、または移行専用の非表示フラグ）。完了（段階5）で初めて通常の visibility どおり公開する。  
旧サイト側の他人向け公開: **退会流用に合わせ、移行中〜済は旧からも見えない**（専用ステータスは作らない＝改修薄く一択）。

#### 旧データの削除タイミング

- **移行中〜新側の確認前:** 旧データは消さない（再実行・照合用）  
- **新側で無事使えていると確認後:** 旧は退会者同様でよい（**メールダミー化・画像削除**）。メモに移行済と残す  
- サイト全体のバックアップ保持は別レイヤ（クローズ後も問い合わせ用に残すかは協議）

「残す」と「使える」は別。移行開始〜完了までは **旧にログインできない**。確認後のスクラブ後もログイン不可のまま。

#### 旧側の状態（専用ステータスは作らない）

**移行専用ステータス（未移行／移行中／移行済／失敗）は旧に足さない。**  
「移行中」は一時用途なので、既存の **解約済み（退会）** に載せて止める。

| タイミング | 旧でのやり方（運用） |
|------------|----------------------|
| 合意〜取込中 | **解約済み**にする → ログイン不可・旧公開からも消える（既存仕様のまま） |
| 管理で分かるように | 表示名を **`〇〇〇〇（移行中）`** 等に変える／**メモ・履歴に代理実行の記録**を残す |
| 新側確認後 | そのまま解約済みでスクラブ可（メールダミー・画像削除）。メモを **「移行済」** に更新 |
| 失敗・取り消し | 解約を解除し、表示名・メモを戻す |

帰結:

- 「並走中も旧で他人に見せ続ける」専用フラグは作らない  
- 二重移行防止・進捗把握は **管理メモ／表示名／新側の取込状態**で足りる  
- 移行中〜新側確認前は画像等は消さない（再取込用）。確認後に退会と同様のスクラブ  

新サイト側の初回ログイン（パス引き継ぎ or 再設定）は協議。  
移行中に新旧とも使えないこと・旧から一時的に見えなくなることは **許容**。

### 裏側（実装のイメージ）

- 既存側から **ユーザー ID 指定で抽出** → 本仕様の形に揃える → **新DBへ取込**（ジョブ本体は新側寄せ）
- 開始時に旧を **解約済み**＋表示名／メモ。完了後はメモを移行済に更新し、確認後スクラブ
- 起動口は **新管理の代理実行**（件数表示と同じ画面。旧に移行ボタンは足さない）
- 旧は抽出API／DB読み出しなど **裏側の最小口**だけ用意すればよい
- 会員向け自己移行は任意・一般期のみ（無くても成立）

### 大口会員（画像1万超・コーデ4桁など）

**移行自体は可能**だが、ボタン1回で同期完了、にはしない。HTTP タイムアウト・メモリ・画像再処理で落ちる。

**運用（推奨）:** 数が大きいユーザーは **個別に案内し、一般オープン前（または自己移行解禁前）に先に移行**させる。その波は **管理画面からの代理移行だけでよい**（マイページ自己移行は必須にしない）。監視しながら1人ずつ／少数並列で回せる。

**勝手移行はしない。** 新系に機能デグレ・未接続があるあいだは、本人（または問い合わせで合意した代理）の意思なく移せない。理想は「こちらで裏側から一人ずつ押すだけ」だが、合意なしのサイレント移行は苦情・データ不整合・「旧でできたことが新でできない」の発覚が重い。  
できること: 合意のとれたユーザーを、管理から **時間をかけて一人ずつ** ジョブ実行する（押す場所は裏側／管理でよい）。できないこと: 全アクティブを無連絡で順次移す。

| やること | 理由 |
|----------|------|
| **ジョブ化（非同期）** | 開始→「移行中」→完了／失敗。進捗が分かるとよい |
| **メタデータ先・画像後**（またはチャンク） | コーデ／アイテム行を先に載せ、画像はキューで順にマスター化 |
| **URL 参照で渡す** | 1万枚のバイナリを1リクエストに載せない |
| **レート制限・リトライ** | CDN／旧オリジン・S3 書き込みを過負荷にしない |
| **再実行してよい（冪等）** | 同じユーザーでもう一度押せる。**既にある ID はスキップ**し、欠け／以前エラー分だけ処理。重複登録しない。途中失敗・手動事前画像の穴埋め・再試行が同じ仕組みになる |

目安:

| 規模感 | 感覚 |
|--------|------|
| 画像 **3桁前半（〜数百）** | ジョブ化は同じでも、多くの場合 **数分以内**で終わりやすい。自己移行解禁後の主対象 |
| 画像 **1万超・コーデ4桁** | **数十分〜数時間＋再処理**。必ず非同期・進捗・再開。**個別案内＋管理代理を先に** |
| **全体（参考）** | 画像おおよそ **33万枚**規模。全件を短期に焼き直すと **数週間〜それ以上**の壁時計になり得る |

**一気にはやらない。** 33万枚・告知集中を踏まえ、**運用で分散**する（方針）。

- 大口は個別合意のうえ管理から先に・少人数ずつ  
- 一般は **代理メイン**（自己は期間限定サブ・任意）。キュー上限で集中を抑える  
- 告知・招待は波分け（クローズド先行→一般、など）  
- 夜間など負荷の低い時間帯に寄せる案も可  

「全件を短期間に裏で焼き切る」はしない。移行期（目安3ヶ月）に分散して消化する。

### 1ユーザーの分割移行（アリ・大口向け）

**1人分をさらに分割してよい。** 特に画像が多い会員は必須に近い。  
ただし「コーデだけ先に新で使える／画像は後」のような **中途半端な利用はしない**（移行中は旧・新とも使えない、の方針を維持）。分割は **裏側の処理単位**であって、ユーザー体験の段階公開ではない。

#### おすすめの段階（設計の骨格）

| 順 | 段階 | 中身 | 完了の印 |
|----|------|------|----------|
| 0 | ロック | 合意済み。旧は **解約済み**＋表示名／メモで区別。新旧とも利用不可 | 旧: 解約＋メモ／新: 取込中 |
| 1 | 会員殻 | `users`（プロフィール・認証に必要な最小） | user 行あり |
| 2 | 投稿メタ | items／coordinates／**紐付け**（どのコーデにどのアイテムか・順序）。画像はまだ旧URL参照でも可 | 件数・紐付け一致 |
| 3 | 画像 | チャンク取得。**投稿済み＝旧 square 由来**、**未使用＝可能ならオリジナル由来**でマスター化。**既存 ID はスキップ**、不足／エラー分だけ取得（再実行可） | 未処理ゼロ |
| 4 | いいね／フォロー | 行はそのまま載せる（先未移行でも可。JOIN で無視＝退会と同じ） | 行投入済み |
| 5 | 確定 | 新側確認 → 旧は退会相当スクラブ可（メモに移行済） | `migrated` |

#### 最大級（例: 約12235枚）の分け方

画像だけ細かく割り、メタはまとめて1段でよいことが多い。

| 塊 | 例 | 重さ |
|----|-----|------|
| 会員＋投稿メタ＋紐付け | 1ジョブ（またはコーデ／アイテムを数千行ずつ） | **相対的に軽い**（DB行のコピー。数万行でも画像より速い） |
| 画像 | **100〜200枚×約60〜120チャンク**（12235なら概ねこの帯） | **重い**（取得・再処理・保存が支配的） |

12235枚の壁時計目安（画像のみ・順次寄り）: 平均2〜5秒/枚なら **約7〜17時間**。チャンク失敗は「その100枚だけ」再実行。夜間に流す／並列2〜3に抑える、など運用で分散。

**紐付け（coordinate_items）も持っていく必要はあるが、画像ほど重くない。**  
必要なのは `coordinate_id` / `item_id` / `sort_order`（またはコーデ側の `item_ids` 配列）。件数はコーデ×平均紐付け数で、1万枚ユーザーでもメタ行は通常「万」オーダーで収まり、バイナリ処理がない。先にメタ＋紐付けを載せ、画像は後から同じ ID に紐づける設計が安全。

ポイント:

- **チェックポイント付きジョブ**（段階・画像チャンク番号を永続化）。落ちても続きから  
- メタ＋紐付け（段階2）→ 画像（段階3）の順。画像だけ分割の主戦場  
- 完了までその1人は常に移行中（中途利用なし）  
- 一般の数百枚は同じ枠組みでチャンクが少ないだけ  

#### 進捗の見せ方（推奨）

**画像とその他を分ける。** メタが先に終わっていれば、残りは画像待ちと明示できる。

| 表示例 | 意味 |
|--------|------|
| 投稿データ: 完了 | 会員・コーデ・アイテム・紐付けまで終わった |
| 画像: 残り 3,420 / 12,235 | **カウントダウン**（未取込枚数） |
| 不足一覧 | まだマスターが無い画像 ID／旧URL（管理・障害切り分け用） |

メタ先載せの利点: 投稿や未使用プールが参照する画像 ID は既に分かっているので、**「どの画像がまだ足りないか」を機械的に列挙できる**（未使用画像も含む）。  
完了条件は「不足一覧が空」。欠番だけ再キューすればよい。  
不足があるあいだは **公開一覧に出さない**（本人ロックとセット。他人に欠け画像を見せない）。

やらなくてよい分割: 会員が「コーデ100件だけ先に移行」を選ぶUI。分割はシステムの内部事情に留める。

### 旧側は最小限（方針）

**旧の改修・開発はできるだけ増やさない。** 足りないものは新側の取込・管理画面、または運用（表示名変更・メモ・手順書）でカバーする。

| やりたいこと | 旧で足すか | 代わり |
|--------------|------------|--------|
| ログイン止め・公開から消す | **既存の解約済みで足りる**（新ステータス不要） | 表示名 `（移行中）`・メモで区別 |
| 代理で移行を回す | **新管理のボタン**（旧に足さない） | 旧は抽出口のみ |
| 履歴・誰がいつ移したか | 専用テーブル不要 | **管理メモ／履歴コメント** |
| 自己移行ボタン | **任意・一般期のみ**。無くても成立 | 問い合わせ→代理 |
| 抽出（メタ＋画像URL） | 必要なら **読み出しだけ**最小 | きれいでない移行専用口でよい |
| 進捗・再開・キュー | **新側に寄せる** | 旧は触らない |

新側に寄せる本丸: 取込 API・画像マスター化・不足一覧・新ログイン。  
旧は「解約にする／表示名とメモを書く／（任意）読み出し口」程度に抑える。

自己移行を付ける場合だけ旧 or 新に導線が増える。集中押し対策（キュー上限・待ち表示・波分け）も **自己移行を付けるとき**の話。代理のみなら運用で分散できる。

## 6. 受け渡しの形（提案）

UI 起動でも、手元検証でも、中身の束は同じでよい。

1. **JSON Lines / JSON 配列**（**ユーザー1人分の束**）  
2. **CSV＋画像ファイルツリー**（ユーザー ID で区切る）  
3. **取込 API**（ユーザー ID 指定。マイページ／管理のボタンから呼ぶ）

画像は「URL 一覧でも可」。受領側で取得・マスター化してよい。  
1人分ロード時に整合（owner が居る／紐付け先がそのセット内 or 既移行）を検証したいです。

## 7. 完了の見え方（受け入れ）

**対象ユーザーごと**に見てよい。

- その移行ユーザーで **新サイトにログイン**できる（または再設定フローが動く）  
- 公開一覧・詳細・マイページが、移行 ID のまま一通り見える  
- いいね／フォロー行は載る（相手未移行・退会相当は JOIN で見えなくてよい。後から自然につながってよい）  
- 仮コーデが公開フィードに混ざらない  
- My*・色調前提のデータが新系に出てこない  
- **現行サイトではその会員がログインできない**（新サイト誘導）
- 新側確認後、旧は退会同様にスクラブしてよい（メールダミー・画像削除）。確認前は消さない

未移行ユーザーは現行のまま。移行済みは新サイトのみ、でよい（サイト全体の DNS 切替とは別レイヤ）。

## 8. まだ協議が必要な一点

| 論点 | 選択肢の例 |
|------|------------|
| パスワード | ハッシュ互換で移す / ユーザー単位で再設定 |
| ID 維持 | 現行公開 ID をそのまま / 新 ID＋対応表 |
| 非公開投稿 | 全部移す / 公開のみ先に移す |
| 画像 | URL から引き直す / ファイル一式をもらう |
| クロップ | 投稿済み＝正方形由来マスター。未使用＝可能なら広い原寸からマスター |
| 移行方式 | **確定: ユーザー単位＋大口案 B**（一括切替は不採用） |
| 大口の事前取込 | **案 B**。手動は Backlog に uid ごと全量／成功／エラー。通常は新管理の同指標＋再実行で 100% |
| 合意なき移行 | しない（デグレ期間は特に）。代理も問い合わせ／個別合意前提 |
| 同時移行の集中 | キュー並列上限・待ち表示・告知の波分け |
| 移行ボタンの置き場 | **代理は新管理で確定**。旧は抽出など最小。自己は一般期のみ・任意 |
| 現行停止の手段 | **解約済み流用で確定**。表示名（移行中）＋メモ／履歴。専用ステータスは作らない |
| 新サイト初回ログイン | パスワード引き継ぎ / 再設定メール |
| 取込失敗時 | 現行のまま残す。同じボタン再実行で既存スキップ＋欠けだけ（冪等）。問い合わせも可 |
| 取込の冪等 | **提案寄り・通常移行の基本**にする（事前画像穴埋めと共通）。メタ行も upsert／既存スキップか要協議 |
| 移行期間の長さ | 3ヶ月目安を前後するか |
| 新の新規登録 | 移行期は閉じる（推奨案）/ 開ける（名寄せ運用が必要） |
| 旧クローズ後のデータ保持 | 問い合わせ移行用に何ヶ月残すか |
| 移行済ユーザーの旧スクラブ | 新側確認後に退会同様（メールダミー・画像削除）。メモは移行済 |
| 移行期の解約 | 同時受付するか／旧・新どちらの導線か／消去範囲 |
| クローズド先行 | やるか／招待人数・期間／一般オープンへの切り替え条件 |
