# 管理機能のエラーアラート設計

**今回のエンジニア引き渡し範囲外**（設計メモのみ。実装は後続）。

`/admin` 本番接続前に決めておく、**運営が気づくべき障害**のメモ。  
チャネル・閾値はインフラ側と合わせる。公開範囲の担保がコストより優先（`OPS_SECURITY.md`）。

関連: [`OPS_SECURITY.md`](./OPS_SECURITY.md) ・ [`WRITE_PATH.md`](./WRITE_PATH.md)

---

## 1. 目的

管理画面や裏方ジョブで起きた失敗を、ユーザー向けフラッシュだけで終わらせず、**運営が追える形**にする。  
ノイズアラートは出さない（常時ON部品・過剰通知は避ける）。

---

## 2. 重要度

| 級 | 意味 | 目安の反応 |
|----|------|------------|
| **P0** | サービス全体・公開範囲・個人情報に関わる | 即時（電話／緊急チャネル可） |
| **P1** | 管理の主要操作が連続失敗／一部機能停止 | 営業時間内に対応 |
| **P2** | 単発失敗・再試行で足りる | 日次ダイジェストで足りることも多い |

---

## 3. 最初に載せる事象（必須候補）

| 事象 | 級 | なぜ必要か |
|------|----|------------|
| 管理ログイン連続失敗（同一 IP／アカウント） | P0/P1 | 総当たり・乗っ取り兆候 |
| 公開↔非公開／削除の更新失敗が続く | P0 | 公開範囲の正が崩れる |
| 画像処理・アップロード失敗率の急増 | P1 | 投稿不能・マスター欠損 |
| DB／API 5xx の急増（管理起点含む） | P0/P1 | 全体影響の入口 |
| 広告案件の公開設定保存失敗 | P1 | 表示事故・収益面 |
| ユーザー強制ログアウト／BAN 操作失敗 | P1 | モデレーション不能 |
| バッチ（集計・クリーンアップ）の失敗 | P1/P2 | 放置すると不整合が溜まる |

WAF／ALB 側のブロック急増はインフラ監視と接続（本リポ外）。未設定のまま公開相当を勧めない（`OPS_SECURITY.md` §4.1）。

---

## 4. 出さない／抑えるもの

- ユーザー側のバリデーションエラー（未入力など）
- 単発の 404・権限不足（操作ミス）
- モック／spike ローカルだけの失敗
- 再試行成功で解消した一時的ネットワークエラー（バースト時だけ上げる）

---

## 5. チャネル案（段階）

| 段階 | チャネル | 備考 |
|------|----------|------|
| 当面 | 運営メール ＋ 管理画面内の「直近エラー」一覧 | 実装が軽い。P0 はメール必須 |
| 次 | Slack／Chat 等の Webhook | メンションルールを級ごとに分ける |
| 本番成熟後 | オンコール（P0 のみ） | 常時待機はコスト大。閾値を厳しく |

管理 UI 上は次を最低限想定する。

1. **操作直後**: 画面内トースト／バナー（利用者向け）
2. **運営向け**: 失敗をサーバ側で構造化ログ（時刻・actor・操作・対象 ID・status）
3. **閾値超え**: 外部通知（上記チャネル）

---

## 6. ログに必ず残す項目

- `at`（ISO 時刻）
- `actor_admin_id`（誰の操作か。システムジョブなら `job:` 名）
- `action`（例: `banner.publish` / `user.ban` / `media.process`）
- `target`（リソース種別と ID）
- `result`（`ok` / `error`）と `error_code`
- 個人情報は載せない（メール全文・本文は出さない）

---

## 7. 受け入れの目安（本番口のとき）

- [ ] P0 相当がメール等で届く（テスト発火できる）
- [ ] 管理の破壊的操作失敗がログに残る
- [ ] 公開範囲変更失敗が埋もれない
- [ ] ノイズ（バリデーション）でチャネルが埋まらない
- [ ] AWS は発注側アカウント。アラート SNS 等も同様（個人アカウントに作らない）

---

## 8. いまのリポでの位置づけ

管理の読み書き口は既に契約／spike にある。本設計は **運用アラート実装を足すときの前提**（引き渡し時点では未実装）。  
UI モック段階では、失敗トーストの文言整理まででよい。通知基盤は接続時に本ドキュメントを正とする。
